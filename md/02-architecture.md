# 목표 아키텍처

## 현재와 목표

현재 코스피 운영 구현은 `core`, `markets/stocks`, `adapters`, `runners`, `reporting`으로 이전했으며 `src/trading/`과 `src/main_scheduler.py`는 호환 진입점을 유지한다. 코인 연결·공통 주문 엔진 전환은 아직 구현되지 않았다. 구체적인 현재 배치는 [전환 현황](07-migration.md)을 따른다.

목표는 공통 운영 기반 하나와 시장별 전략·정책, 거래소별 연결 모듈을 조합하는 구조다.

```text
src/
  core/
    models/          # 상품·시세·신호·주문·체결 계약
    ports/           # 데이터·계좌·주문·정책 인터페이스
    execution/       # 주문 상태와 체결 반영
    risk/            # 공통 검사 절차
    observability/   # 이벤트·스냅샷·작업 기록
    audit/           # 독립 검사 실행
    research/        # 재현·성과 집계
  markets/
    stocks/          # 코스피 선정·지표·전략·위험·청산·거래일
    crypto/          # 코인 선정·지표·전략·위험·청산·연속 운영
  adapters/
    kis/             # 인증·시세·계좌·주문 API 변환
    crypto_exchange/ # 거래소 확정 후 실제 이름으로 생성
  runners/
    stocks.py
    crypto.py
    audit.py
  reporting/         # 시장별·통합 조회
tests/
  core/
  markets/
  adapters/
  integration/
md/                  # 현재 지침·목표 설계
docs/                # 분석·실험·검증 증거
```

위 트리는 목표다. 빈 모듈 생성만으로 구현 완료를 표시하지 않는다.

## 의존 방향

- `core`는 표준 계약·인터페이스를 정의하며 `markets`, `adapters`, `runners`에 의존하지 않는다.
- `markets`는 공통 계약을 사용하고 전략과 정책을 제공한다. 거래소 SDK를 직접 사용하지 않는다.
- `adapters`는 공통 인터페이스를 구현하고 외부 API를 공통 자료형으로 변환한다. 전략 판단을 수행하지 않는다.
- `runners`가 시장 정책·연결·저장소를 조립하고 실행 순서를 관리한다.
- `reporting`은 조회와 보고를 담당한다. 화면 조회를 매매 실행의 부수 효과로 연결하지 않는다.

## 공통 실행 절차

데이터 검증 → 시장 상태 평가 → 종목 평가 → 가상 배분 → 주문 허용·위험 검사 → 주문 의도 저장 → 제출 → 체결 대조 → 장부 반영 → 사후 점검.

시장 약세로 신규 주문을 막아도 유효한 데이터로 종목 평가는 지속한다. 데이터 부족은 해당 단계의 미확인으로 남긴다. 신규 진입 차단은 기존 포지션 청산을 차단하는 조건으로 사용하지 않는다.

## 분리 단위

공통화: 기록 형식, 주문 상태 전이, 중복 방지 원칙, 검증 실행, 재현 실행, 기본 수학 함수.

시장별 분리: 투자 대상, 거래 시간, 봉 확정, 지표 조합, 배점, 비용 모델, 포지션 비중, 진입·청산 규칙.

거래소별 분리: 인증, API 제한, 주문 규격, 응답 상태, 체결·잔고 대조.

주식과 코인의 실행 프로세스·예산·장부는 분리한다. 공통 형식의 로그와 통합 읽기 화면을 사용하되 한쪽 장애가 다른 쪽 작업을 중단시키지 않도록 구성한다.
