# 퀀트 매매 시스템 보완 및 로그 기반 자체 점검 계획

작성일: 2026-09-09

## 1. 목표와 범위

현재 자동매매의 데이터, 선정, 점수, 배분, 주문, 청산, 검증, 변경, 운영 관리 기능을 보완한다. 각 변경은 적용 버전과 실제 입력·판단·결과를 기록하며 별도 점검기가 독립적으로 검증한다.

이 문서는 수정 계획이다. 운영 코드·설정·서비스·주문을 변경하지 않는다. 파일 경로와 이벤트 이름은 구현 시 사용할 제안이다.

완료는 다음 네 가지를 구분한다.

1. 구현 완료: 코드와 의미 있는 테스트가 통과했다.
2. 적용 확인: 실제 실행 프로세스가 기대한 코드·설정 버전을 읽었다.
3. 동작 확인: 실제 또는 명시된 모의 실행에서 입력→판단→결과가 점검 규칙과 일치했다.
4. 성과 검증: 변경에 사용하지 않은 기간에서 비용 후 성과·위험을 평가했다.

1~3 통과를 수익성 검증 완료로 표시하지 않는다. 실제 주문이 없었다면 체결 기능은 모의 검증 완료, 실거래 미관측으로 구분한다.

## 2. 현재 확인된 출발점

- morning_screener.py:476은 전일 일봉 거래량을 장중 기대 비중으로 환산한다. 당일 누적 거래량 입력으로 수정해야 한다.
- main_scheduler.py:188은 아침 실행 출력의 마지막 6,000자만 저장한다. 전체 후보와 점수 재현에 필요한 자료가 손실된다.
- main_scheduler.py:274의 정기 Heartbeat 문구는 매매·수집·체결의 정상 동작을 증명하지 않는다.
- kis_trader.py는 체결 조회 실패 시 현재가로 거래를 기록하는 경로가 있다. 확정 체결과 추정치를 분리해야 한다.
- trade_analyst.py는 최근 승률이 낮으면 기술 비중을 높인다. 원인과 변경 효과를 검증하는 절차로 대체해야 한다.
- 과거 9월 7~8일 분석은 관측 가능한 일부 후보의 비교다. 소실된 과거 원점수와 입력은 현재 정보로 채우지 않는다.

## 3. 공통 기록과 점검 구조

### 3.1 기록의 역할

- 사람이 읽는 기존 운영 로그: 상황과 오류의 요약.
- 구조화 이벤트: 판단·주문·체결·점검의 원본 기록. SQLite의 별도 audit.db에 저장하고 일자별 JSONL로 내보낸다.
- 입력 스냅샷: 당시 시세·거래량·뉴스 평가·재무 근거·후보군·설정의 날짜별 보관본.
- 별도 점검기: 스케줄에 맞춰 이벤트와 스냅샷을 읽고, 필요한 경우 증권사의 읽기 전용 조회 결과와 대조한다.
- 점검 결과: 기계용 JSON과 사용자용 일별 요약. 원본 이벤트 ID와 근거 파일을 연결한다.

실거래 경로는 감사 이벤트를 성공적으로 보존한 후 신규 주문 의도를 외부에 전달한다. 저장 실패 시 신규 매수는 제한한다. 기존 보유분의 위험 감시는 계속하며, 청산 시 기록 실패를 이유로 보호 동작을 무조건 막지 않는다. 가능한 보조 기록에 남기고 복구 후 대조한다.

서로 다른 DB와 증권사 주문을 하나의 트랜잭션으로 묶을 수 있다고 가정하지 않는다. 주문 의도와 결과 사이의 중단을 복구할 수 있도록 영속 주문 상태와 대조 절차를 둔다.

### 3.2 공통 이벤트 필드

| 묶음 | 필드 예시 | 목적 |
|---|---|---|
| 식별 | event_id, run_id, session_id, decision_id, position_id | 실행·판단·보유 생명주기 연결 |
| 주문 | client_intent_id, broker_order_id, fill_id | 재시도·부분 체결·취소 대조 |
| 시간 | event_time_utc, trading_date_kst, source_time, received_time | 거래일과 데이터 지연 확인 |
| 버전 | schema_version, code_version, effective_config_hash, strategy_version, model_version | 실제 적용한 변경 확인 |
| 입력 근거 | snapshot_id, symbol, market, source, input_asof | 판단 재현 및 미래정보 혼입 검사 |
| 판단 | stage, event_type, outcome, reason_code, rule_values | 통과·탈락·오류의 원인 설명 |
| 점검 | check_id, expected, observed, tolerance, status, evidence_ids | 자동 판정의 근거 보존 |

실행 시 읽은 실효 설정을 저장한다. 파일의 현재 내용이나 git 커밋만으로 적용을 판정하지 않는다. 배포 파일 해시와 프로세스 시작 시각도 남겨 미커밋 변경·재시작 누락을 식별한다.

인증키·토큰·비밀키·전체 계좌번호는 기록하지 않는다. API 원문 전체 대신 가격·수량·상태 등 검증에 필요한 필드만 허용 목록으로 보존한다. 실거래, 모의, 과거 재현은 execution_mode로 구분한다.

### 3.3 상태 판정

| 상태 | 의미 |
|---|---|
| PASS | 필요한 증거가 있고 규칙이 일치함 |
| FAIL | 관측 결과가 명시된 규칙을 위반함 |
| WARN | 동작은 가능하지만 지연·품질 저하 등 검토가 필요함 |
| UNKNOWN | 로그 누락, 외부 조회 불가, 미확정 주문 등으로 판정 불가 |
| N/A | 휴장일 또는 해당 거래 미발생 등으로 적용 대상이 아님 |

오류 문구가 없다는 이유로 PASS를 부여하지 않는다. 필수 이벤트가 마감 시각까지 없으면 UNKNOWN 또는 작업 미완료 FAIL이다. 데이터 도착 허용시간, 체결 반영 유예시간, 금액 반올림 허용오차는 점검별 버전 설정으로 명시한다. API가 응답하지 않으면 이전 정상 결과를 새 PASS로 재사용하지 않는다.

점검기는 운영 코드가 출력한 PASS를 신뢰해 전달하지 않는다. 원본 입력과 별도 계산 또는 증권사 조회를 사용한다. 다만 로그만으로 외부 데이터의 진실성·미래 수익성을 완전히 보장할 수는 없다.

## 4. 영역별 수정·기록·자동 점검

### A. 데이터 품질과 재현성 — DQ

수정:
- 당일 KRX 누적 거래량과 전일 기준 평균 거래량을 시점에 맞춰 사용한다.
- 시세 조회 시 현재가·누적 거래량·기준 시각을 함께 확보하고, 지연 허용 범위를 넘으면 새 신호 생성을 제한한다.
- 캐시를 날짜·스키마·기준시각별로 보관한다. 액면분할 등 가격 조정 기준과 시장 구분도 저장한다.
- 뉴스는 발행 시각뿐 아니라 최초 수집 시각, 모델·프롬프트 버전, 점수·신뢰도·기사 수를 보관한다.

이벤트: DATA_SNAPSHOT, DATA_VALIDATION, DATA_REJECTED.

점검:
- DQ-01: 거래량 입력의 거래일이 판단 거래일과 같은지 확인한다.
- DQ-02: 분봉 누적 합과 시세 API 누적값을 동일한 시장·마감 시각에 맞춰 비교한다. 집계 범위 차이를 먼저 제거한다.
- DQ-03: 데이터가 판단보다 미래이거나 너무 오래됐는지 검사한다.
- DQ-04: 0·음수·결측값, 설명되지 않은 누적 거래량 감소, 캐시 날짜 불일치를 탐지한다.

통과 기준: 알려진 고정 입력에서 올바른 SD 값을 계산하고, 전일 거래량·오래된 시세를 주입하면 해당 검사와 진입 제한이 작동한다. 만점 종목 수가 적다는 것 자체를 정답으로 삼지 않는다.

### B. 투자 대상과 필터 — UN

수정:
- 분석 시장, 종목 유형, 유동성 기준, 예산 제한을 명시한다.
- 필터를 거래 불가·데이터 부족·전략 비선호로 나누고 실행 순서를 고정한다.
- 최초 종목 풀부터 각 단계 통과·탈락 목록까지 저장한다. 미매수도 명시적 결과로 남긴다.

이벤트: UNIVERSE_CREATED, FILTER_EVALUATED, CANDIDATE_ACCEPTED, CANDIDATE_REJECTED, NO_TRADE_DECISION.

점검:
- UN-01: 각 단계 입력 수 = 통과 수 + 탈락 수 + 미확정 수인지 확인한다.
- UN-02: 제외 종목마다 규칙 ID, 비교값, 사유가 존재하는지 확인한다.
- UN-03: 자료가 있는 후보가 이유 없이 사라지거나 중복되면 실패 처리한다.
- UN-04: 무거래가 점수 미달인지 데이터 실패인지 구별한다.

통과 기준: 전체 후보의 최종 상태를 설명할 수 있다. 후보 0건과 분석 실패를 같은 정상 무거래로 처리하지 않는다.

### C. 신호와 점수 — SG

수정:
- 세부지표, 기술·감성·재무 원점수, 가중치, 임계값을 반올림 전 정밀도로 저장한다.
- 점수 계산을 주문 기능과 분리된 순수 함수로 구성한다.
- 감성 중립·뉴스 부족·모멘텀 감점·가격 변동폭 필터의 의미를 명시한다.
- 거래량 수정 후 점수 분포와 임계값을 함께 재검증한다. 0.70을 상승 확률로 표시하지 않는다.

이벤트: SIGNAL_INPUT, SCORE_COMPUTED, SIGNAL_ACCEPTED, SIGNAL_REJECTED.

점검:
- SG-01: 별도 점검기가 저장된 원점수·가중치로 합계를 재계산한다.
- SG-02: 허용 범위, 유한한 수치, 가중치 합, 필터·문턱 경계의 비교 연산을 검증한다.
- SG-03: 같은 스냅샷·버전으로 재실행했을 때 같은 판단인지 확인한다. LLM은 당시 저장 결과를 재사용한다.
- SG-04: 특정 지표의 만점 고정·결측 급증은 분포 이상 WARN으로 표시하고 원본 입력 검사를 병행한다.

통과 기준: 기준 바로 아래·동일·바로 위의 경계 사례와 누락 입력을 올바르게 처리한다. 점수 일치와 수익성은 별도 항목이다.

### D. 자금 배분과 포트폴리오 — PF

수정:
- 점수 초과분 배분과 위험 기반 배분을 별도 비교안으로 검증한다.
- 종목별·계좌별 손실 한도, 투자금 상한, 업종·테마 집중도를 관리한다.
- 한도의 기준이 현금인지 총자산인지 명시하고, 해당 판단에 사용한 계좌 스냅샷을 저장한다.
- 미체결 주문 예약금, 비용, 정수 주식 제약, 최소 현금을 반영한다. 1주 예외도 모든 상한 검사를 거친다.

이벤트: ACCOUNT_SNAPSHOT, ALLOCATION_PROPOSED, RISK_CHECKED, FUNDS_RESERVED, FUNDS_RELEASED.

점검:
- PF-01: 주문·미체결 예약금·예상 비용을 포함한 자금 사용이 가용액을 넘지 않는지 검사한다.
- PF-02: 종목·계좌·일별 매수 수·집중 한도를 재계산한다.
- PF-03: 부분 체결·취소 이후 예약금 해제가 올바른지 확인한다.

통과 기준: 비싼 종목 1주, 동시 주문, 부분 체결, 취소 사례에서 중복 배정과 한도 우회를 막는다. 손절가 기반 예상손실은 실제 최대손실 보장으로 표시하지 않는다.

### E. 주문과 체결 — EX

수정:
- 영속 주문 상태를 의도 생성→전송 중→접수/거절/응답 불명→부분 체결→완료/취소로 관리한다.
- client_intent_id로 내부 중복 실행을 막는다. API 타임아웃 이후 증권사 조회로 확인하기 전 동일 주문을 맹목 재전송하지 않는다.
- 체결 확인 실패는 미확정으로 남기며 현재가를 확정 체결가·손익에 넣지 않는다.
- 매수와 매도에 같은 주문 관리자와 대조 절차를 적용한다.

이벤트: ORDER_INTENT, ORDER_SUBMITTED, ORDER_ACK, ORDER_UNKNOWN, FILL_RECEIVED, CANCEL_REQUESTED, ORDER_CLOSED, RECONCILED.

점검:
- EX-01: 동일 의도에 중복 외부 주문이 생겼는지 검사한다.
- EX-02: 체결 수량 합이 주문량을 넘지 않는지, 평균 체결가와 금액이 일치하는지 검사한다.
- EX-03: 미확정 주문을 확정 거래에 합산하지 않았는지 확인한다.
- EX-04: 증권사 체결과 로컬 주문·체결·보유를 유예시간 후 대조한다.

통과 기준: 주문 접수 후 응답 유실, 중복 응답, 부분 체결, 취소 실패, 프로세스 중단을 모의 주입해 복구를 확인한다. 식별이 불가능한 주문은 UNKNOWN으로 남기고 신규 노출을 제한한다. 점검을 위해 불필요한 실거래를 만들지 않는다.

### F. 청산과 계좌 위험 — RK

수정:
- 기존 +5%/-3%/시간 청산을 기준안으로 재현하고 다른 청산 방식은 별도 실험한다.
- 청산 판단과 주문 실행을 분리하며, 동일 보유분의 중복 매도와 손절 직후 의도치 않은 재진입을 방지한다.
- 계좌 손실 한도, 시세 지연, 미확정 주문, 잔고 불일치별 대응 정책을 둔다.
- 청산 명령과 청산 완료를 구분하고, 시간 청산 실패 후 재조회·알림·재시도 정책을 명시한다.

이벤트: POSITION_MARKED, EXIT_TRIGGERED, EXIT_PENDING, POSITION_CLOSED, ENTRY_BLOCKED, RISK_LIMIT_BREACHED.

점검:
- RK-01: 해당 시점 시세와 원가로 익절·손절 조건을 재계산한다.
- RK-02: 조건 충족→판단→주문→체결의 시간 지연을 각각 검사한다.
- RK-03: 청산 목표 시각 후 잔고와 미체결 매도 주문을 조회한다. 매도 요청 로그만으로 완료 판정하지 않는다.
- RK-04: 진입 제한 상태에서 새 매수가 발생하지 않는지 검사한다.

통과 기준: 위험 조건 충족 시 행동이 일치하고, 재시작 후 보유·미확정 주문을 복원한다. 잔고를 모르는 상태에서 무조건 전량 매도하거나 가격을 모르는 상태에서 임의 가격으로 정상 청산을 가정하지 않는다.

### G. 재현·백테스트·성과 — BT

수정:
- 실거래와 과거 재현에서 동일한 신호·배분·청산 코드를 사용한다. 주문 어댑터만 다르게 한다.
- 과거 재현의 데이터는 당시 시점 기준으로 제한하며 체결 비용·세금·가격 미끄러짐·부분 체결을 모델링한다.
- 분석에 사용한 기간과 이후 검증 기간을 분리한다. 파라미터 선택 이력을 보존한다.
- 거래당 기대손익, 최대 낙폭, 손익비, 비용, 거래 수, 자금 사용률을 함께 보고한다.

이벤트: REPLAY_STARTED, REPLAY_DECISION, BACKTEST_COMPLETED, METRIC_COMPUTED, VALIDATION_RESULT.

점검:
- BT-01: 같은 당시 입력에서 실거래 판단과 재현 판단이 일치하는지 비교한다.
- BT-02: 원장으로 순손익·잔고·수익률을 독립 재집계한다. 입출금은 매매손익과 분리한다.
- BT-03: 검증 기간 침범, 미래 뉴스·공시 혼입, 손절/익절 선후를 알 수 없는 분봉을 탐지한다.
- BT-04: 무거래일의 승률을 0%로 넣지 않고 N/A 처리한다.

통과 기준: 재현 오차의 원인을 설명하고, 사전에 정한 비용·위험·표본 기준으로 성과를 판단한다. 합성 테스트 수익이나 이틀의 좋은 성과를 실전 유효성으로 인정하지 않는다.

### H. 전략 변경과 배포 — CH

수정:
- 최근 승률만으로 배점을 바꾸는 경로를 실험 제안 절차로 대체한다.
- 변경 ID, 가설, 적용 파일, 기대 효과, 검증 기준, 결과, 복구 버전을 기록한다.
- 기준 전략 대비 평가 후 주문 없는 병행 계산→모의 운용→제한된 실거래 관측으로 확인한다.
- 계산 오류 수정도 점수 분포·거래 횟수를 바꾸므로 적용 전 영향 비교를 수행한다.

이벤트: CHANGE_PROPOSED, CHANGE_TESTED, RELEASE_ACTIVATED, PROCESS_CONFIG_LOADED, RELEASE_ROLLED_BACK.

점검:
- CH-01: 기대 배포 해시와 실제 각 프로세스의 코드·실효 설정·모델 버전을 비교한다.
- CH-02: 검증되지 않은 설정 변경과 버전 혼용을 탐지한다.
- CH-03: 복구가 신규 진입 정책을 되돌리더라도 기존 보유·주문 상태를 버리지 않는지 확인한다.

통과 기준: 프로세스별 적용 상태를 표시하고, 복구 후 주문 중복 없이 운영 상태를 보존한다. 자동 점검기가 임의로 가중치를 최적화·배포하지 않는다.

### I. 사후 분석과 운영 점검 — OP

수정:
- Heartbeat를 프로세스 생존, 작업 완료, 데이터 최신성, 주문·잔고 일치, 위험 대응 상태로 분리한다.
- 거래일 캘린더와 예정 작업 목록으로 누락된 수집·평가·청산·점검을 찾아낸다.
- 미매수 후보도 사전에 정한 동일 규칙으로 추적한다. 입력 부족 시 가상 수익 확정을 보류한다.
- 점검기의 실행·완료 여부도 별도 감시하고 로그 순번·필수 이벤트·스냅샷 존재 여부를 검사한다.

이벤트: JOB_EXPECTED, JOB_STARTED, JOB_FINISHED, AUDIT_STARTED, AUDIT_FINISHED, AUDIT_FINDING, DAILY_REVIEW.

점검:
- OP-01: 예정 작업이 기한 내 완료됐는지와 필수 입력·산출물이 존재하는지 확인한다.
- OP-02: 점검기 종료 코드와 마지막 완료 시각을 별도 스케줄러가 확인한다.
- OP-03: 모든 판단에 최종 사유가 있고 모든 주문에 최종 상태 또는 미확정 사유가 있는지 확인한다.
- OP-04: 원본 스냅샷을 가리키는 링크가 유효하고 보관 정책에 따른 삭제가 분석 재현을 깨지 않는지 확인한다.

통과 기준: 시스템이 멈추거나 점검기가 죽어 로그가 없을 때 정상으로 보이지 않는다. 정상 무거래, 데이터 불량 무거래, 프로세스 미실행을 구분한다.

## 5. 점검 실행 시점과 대응

| 시점 | 점검 | 결과 활용 |
|---|---|---|
| 프로세스 시작·배포 직후 | 버전·설정, DB 접근, 이전 미확정 주문, 계좌 대조 | 신규 진입 가능 상태 결정 |
| 장전 수집 완료 후 | 데이터 시점·누락, 종목 풀, 시장·거래일 | 아침 평가 시작 가능 여부 |
| 평가 종료 후·주문 전 | 단계별 후보 수, 점수 재계산, 예산·위험 한도 | 잘못된 주문 차단 |
| 주문·체결 이벤트마다 | 상태 전이, 중복, 수량·금액, 예약금 | 미확정 처리·대조·노출 제한 |
| 장중 감시마다 | 시세 최신성, 손절·익절, 계좌 위험, 감시 지연 | 청산 판단 및 신규 진입 제한 |
| 시간 청산 후 | 실제 잔고·미체결 주문·체결 확정 | 청산 완료 또는 미완료 보고 |
| 장후 | 원장 대조, 비용 후 성과, 미매수 비교, 작업 누락 | 일별 보고서 |
| 주간·전략 변경 전후 | 분포 변화, 실거래/재현 차이, 변경 효과 | 검토 과제와 배포 판단 근거 |

신규 주문 전 한도 검사는 실거래 경로에서 즉시 실행한다. 별도 점검기는 이를 사후 독립 검증한다. 장후 로그 검사만으로 이미 발생한 위험을 막았다고 간주하지 않는다.

기능별 필수 FAIL 또는 핵심 UNKNOWN이 있으면 그 기능을 정상으로 표시하지 않는다. 정상 거래를 관측하지 못했다는 이유만으로 전체 시스템 장애로 판정하지 않고, 실거래 검증 범위의 부족으로 별도 표시한다.

## 6. 구현 순서와 단계별 통과 조건

| 단계 | 작업 묶음 | 통과 조건 |
|---|---|---|
| 0. 기준 보존 | 현행 코드·설정·DB 스키마·대표 실행 기록 보존, 점검 규칙 ID 확정 | 기존 동작과 변경 후 동작을 비교할 기준 확보 |
| 1. 공통 기록·점검 기반 | 이벤트 저장, 스냅샷, 변경 버전, 작업 완료 감시, 점검 결과 포맷 | 로그 누락·버전 불일치·점검기 실패가 정상으로 처리되지 않음 |
| 2. 데이터·거래 사실성 | 거래량 오류, 시점 검사, 체결 미확정 분리, 주문·잔고 대조, 재시도 관리 | 과거 입력 재현 및 모의 장애 시나리오 통과 |
| 3. 판단·위험의 재현 | 후보 흐름, 점수, 자금 배분, 청산 공통화와 즉시 한도 검사 | 독립 재계산 일치, 한도 위반 차단, 재시작 복구 통과 |
| 4. 전략 검증 | 현실적인 백테스트, 비용·낙폭·미매수 분석, 기존 전략 기준 성과 | 계산 정확성과 성과 평가를 분리한 보고서 산출 |
| 5. 전략 개선·단계 적용 | 배점/임계값/배분/청산 비교, 이후 기간 검증, 변경·복구 절차 | 사전 기준 충족, 적용 버전 확인, 관측 범위 명시 |

전체 시스템을 한 번에 교체하지 않는다. 기록 추가는 기존 판단과 병행하며, 거래 판단을 바꾸는 수정은 재현 비교와 버전 적용 확인을 거친다. 여러 주의 성과 표본이 필요하면 구현·모의 검증 완료 상태로 두고 실전 성과 검증은 진행 중으로 표시한다.

## 8. 최소 장애·경계 검증 목록

- 전일 거래량, 오래된 현재가, 뉴스 수집시각 누락을 주입한다.
- 점수가 문턱 바로 아래·동일·바로 위인 사례를 검사한다.
- 후보 전체 탈락과 분석 실패를 각각 실행한다.
- 예산 경계의 1주 주문, 미체결 예약금이 있는 추가 주문을 검사한다.
- 주문 응답 유실, 부분 체결, 취소 실패, 중복 응답을 모의 실행한다.
- 주문 전송 직후·부분 체결 직후 프로세스를 중단하고 복구한다.
- 손절과 시간 청산 동시 발생, 청산 주문 미체결을 검사한다.
- 이벤트 저장 실패, 로그 잘림, 필수 이벤트 삭제, 점검기 중단을 검사한다.
- 실효 설정은 이전 버전인데 배포 파일만 바뀐 상황을 검사한다.
- 휴장일, 무거래일, 입출금, 거래비용 반영 지연을 검사한다.

모의 증권사 어댑터와 테스트 DB에서 수행하며 운영 계좌에 장애 시험 주문을 보내지 않는다. 기대값이 있는 고정 자료와 별도 원장 재계산을 사용해 구현을 그대로 복사한 테스트만으로 정상 판정하는 것을 피한다.

## 10. 최종 인수 조건

- 변경별 구현·적용·동작·성과 상태가 구분되어 있다.
- 필요한 로그가 없으면 정상 판정을 내리지 않는다.
- 모든 매수·미매수 판단을 당시 입력과 설정으로 설명할 수 있다.
- 모든 주문을 증권사 상태와 연결하고 미확정 거래를 숨기지 않는다.
- 데이터·점수·수량·청산을 독립적으로 재계산하고 오류를 탐지한다.
- 점검기 자체의 누락과 프로세스 버전 불일치를 탐지한다.
- 실거래·모의·재현의 검증 범위를 분리한다.
- 자동 점검 통과가 미래 수익이나 전략 최적성을 보장한다고 표시하지 않는다.
